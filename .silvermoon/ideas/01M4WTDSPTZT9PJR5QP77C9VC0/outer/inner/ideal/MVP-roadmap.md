# Gate 的 MVP 迭代路线

当前 `gate-service`
保留为**阶段 4 的最终完整服务**，不是要求第一轮做完的实施集合。前三个前置 Idea 分别交付一个可用闭环；每个都独立经过构想、实现与试点部署验收。

## 顺序与闭环

| 顺序 / Idea                                                                                 | 这一轮新增的可用结果                                                                            | 完成证明                                                       | 明确不做                                        |
| ------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- | -------------------------------------------------------------- | ----------------------------------------------- |
| 1 · [gate-mvp-human](../../../../01M4XC32C5CB66DH8RFWPCAEF1/outer/inner/ideal/Idea.md)      | 人类登录 → 创建固定载荷请求 → 另一合格人类批准/拒绝 → 请求方查看或撤回 → 留下历史               | 真实双人受限在线试点，幂等/终态竞争/审计一致性证明             | Agent、委托、签名/离线、模板后台、强认证保证    |
| 2 · [gate-mvp-agent](../../../../01M4XC5P9EQ0K1PCY16K5JF0D3/outer/inner/ideal/Idea.md)      | Agent 独立认证发起 → 人类审批 → 调用方核对在线状态与摘要后恢复                                  | 一个真实 PGH/Agent 工作流含断网/失效/拒绝的不放行演练          | Delegate/Grant、Agent 自审批、离线验证、Webhook |
| 3 · [gate-mvp-credential](../../../../01M4XC85F6TXF4XSZQMZ6X1F2W/outer/inner/ideal/Idea.md) | 决定 → 可靠签发 → 导出凭证 → Gate 不可达时独立核验并放行                                        | 跨实现签名向量、签发恢复、断线验证、泄露 keyId/旧快照案例      | 委托、复杂 MFA、全量管理后台                    |
| 4 · [gate-service](Idea.md)                                                                 | 在前三轮上完成有界 Delegate/Grant → 归属明确的审批 → 历史凭证；补齐模板 MFA、管理 UX 和生产运维 | 委托/撤销/到期/越界并发测试，生产调用方试点、密钥/状态恢复演练 | 会签、多租户、流程引擎、转委托（第一版关闭）    |

依赖为 **1 → 2 → 3 →
4**。依赖由本路线和各 Idea 的边界明确表达，不新增未受支持的 Silvermoon
schema 字段。不能把“构想已提交”当成“前置阶段已完成”；进入下一轮实际实施前，前一轮实现与部署均应完成并获对应验收。当前仅拆分计划，没有接受任何新 revision，也没有开始实现。

## 为什么这样拆

- 按用户价值纵向切片，不按“数据库 → API →
  UI”分层：每轮同时有必要的界面/接口、状态、安全边界和真实试点。
- 在线人类审批可以先服务低风险场景；Agent 接入才引入 workload 认证，离线凭证才引入密钥和签发恢复，委托才引入授权图，避免第一轮同时处理所有难点。
- 直接权限并不等于隐式继承：前三轮 authority=actor，所有业务权限仍需明确分配。第 4 轮扩展到委托关系，不重写此前身份或历史决定。
- 缩小功能而不省略正确性：从第 1 轮起固定身份/载荷/版本、逐请求访问控制、幂等和唯一终态；每轮新增能力要回归前轮闭环。

## UX 的阶段投影

现有 [UX 设计](UX.md) 与 [七个场景示意](ui-review/index.html)
仍是最终体验，不要求 MVP 1 同时上线。

- **MVP 1：**
  登录、创建、我的请求、待我审批、详情确认、撤回与逐请求历史。模板和名单可由受控运维配置，不先建设发布后台；界面不出现可用的委托或凭证下载入口。
- **MVP 2：**
  最小 Agent 注册/认证交付及调用方接入示例，详情识别 Agent 发起方；无需完整身份/绑定管理页面。
- **MVP 3：**
  凭证待签发/失败/就绪、导出及独立验证解释，基础密钥/信任包运维；不能把签发状态合并成“已批准即可离线”。
- **最终阶段：**
  Delegate/Grant、身份绑定/轮换/封存、模板版本/名单管理、MFA、授权证据与生产运维界面，复用前三轮能力。

## 数据、协议与发布边界

复用
[技术选型](Tech-stack.md)，按需引入组件与状态层，不一次创建全量包/表/接口。初期 D1、React、shadcn/ui 和一个人类认证入口足以形成第一轮闭环；跨页 UI
store、Agent token、outbox 和签名模块在对应阶段需要时才增加。

每次数据/接口变更应版本化并回归既有请求；旧阶段的历史凭证或身份不得被伪造补齐。已有半成品可复用，但不替代新阶段的验收证明。MVP
1/2 仅在线使用，受限环境的保证不能宣传成最终服务的离线/MFA/生产保证。

生产主机名与完整恢复验收属于最终阶段，前置轮次允许在明确归属的隔离测试环境部署。对外说明当前可用能力和不适用场景，后轮试点仍需重复验证前轮功能；每次发布均保留审计、权限、迁移与失败恢复的必要检查。

## 首轮审阅范围

先审阅 `gate-mvp-human`
的最小闭环；另外两张前置方向卡和最终路线用于确认顺序，不代表必须提前接受其未来实现细节。第一轮完成后再按试点反馈细化下一轮，而不是预先写完全部实施任务。
